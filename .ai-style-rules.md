## [Naming & State-Control Rules]

- Use PascalCase for exported React components and their data types; use camelCase for functions, values, props, and state.
- Keep portfolio content in typed module-level arrays above the component that renders it.
- Order portfolio files as imports, local types, content/constants, then the exported component.
- Model optional content with optional typed fields and render it conditionally instead of creating placeholder links or text.
- Name local UI state for the value it holds (`filter`, `active`, `loading`, `submitting`) and pair it with the conventional `set...` setter.
- Keep visual states in existing Tailwind utility patterns and project CSS variables; use item-level color fields for project-specific accents.
- Use `motion` and `AnimatePresence` only where adjacent portfolio sections already use them, with restrained transitions and `viewport={{ once: true }}` for scroll reveals.
- Keep shared primitives in `src/app/components/ui`, portfolio sections in `src/app/components/portfolio`, imported media in `src/imports`, and cross-cutting CSS in `src/styles`.
- Handle network errors at the async boundary with `try/catch`, restore loading state, and surface a user-readable result.

## [DONTs]

- Do not introduce a new component architecture for a single portfolio entry; extend the existing typed data model and renderer.
- Do not mix the generated UI primitive formatting style into hand-written portfolio components, or vice versa.
- Do not add dead `#` links for unavailable demos or source repositories.
- Do not duplicate shared section, button, or dialog markup when an existing primitive already provides it.
- Do not hard-code a new global color when an existing theme variable or per-item accent is sufficient.
- Do not alter unrelated user changes while editing a focused portfolio feature.
- Do not expose credentials, local configuration values, or private deployment details in client-side portfolio content.
